  Propósito del Proyecto

  Este es un sistema de control y monitoreo para un Robot Móvil Autónomo (AMR), específicamente un TurtleBot3,
   como se infiere por el directorio turtlebot3-sim. El proyecto permite a un usuario interactuar con el robot
   a través de una interfaz web.

  Arquitectura

  El sistema está orquestado con Docker Compose y se compone de tres partes principales que se comunican a
  través de una red Docker (ros_net):

   1. Interfaz de Usuario (Frontend - `ui_web`):
       * Es una aplicación de una sola página (SPA) construida con React y Vite.
       * Utiliza Leaflet y react-leaflet para mostrar mapas interactivos, que son cruciales para la
         visualización de la posición del robot y su entorno.
       * Incluye un componente de joystick virtual (react-joystick-component), lo que indica que los usuarios
         pueden controlar manualmente el robot desde la web.
       * Se comunica directamente con el robot (o la simulación) a través de WebSockets usando roslib para
         obtener datos en tiempo real (ej. posición, estado) y enviar comandos de control.
       * También se comunica con la API Backend para operaciones como la gestión de mapas o misiones.

   2. API (Backend - `api`):
       * Es un servicio RESTful construido con Python y FastAPI.
       * Utiliza MongoDB como base de datos (a través de Beanie y Motor) para persistir información como
         mapas, misiones, usuarios, etc.
       * Implementa un sistema de autenticación de usuarios con JWT (python-jose y passlib).
       * Actúa como un intermediario que también puede comunicarse con el entorno ROS a través de roslibpy,
         permitiendo realizar operaciones más complejas o que requieren lógica de negocio en el servidor.

   3. Simulación (`turtlebot3-sim`):
       * Este servicio ejecuta la simulación del robot en un entorno ROS (Robot Operating System).
       * Expone un servidor rosbridge (WebSocket), que es el puente de comunicación clave que permite que las
         aplicaciones no-ROS (como la web y la API) se comuniquen con el ecosistema ROS.

  Flujo de Trabajo de Desarrollo

  El proyecto está muy bien configurado para el desarrollo:

   * Producción/Base: Los archivos docker-compose.yml y docker-compose.api.yml definen la estructura base,
     usando una imagen de Nginx para servir la versión compilada de la UI.
   * Desarrollo: El archivo docker-compose.override.yml modifica la configuración para el desarrollo local,
     habilitando live-reload tanto para el frontend (con el servidor de desarrollo de Vite) como para el
     backend (con uvicorn --reload). Esto permite que los cambios en el código se reflejen instantáneamente
     sin necesidad de reconstruir las imágenes de Docker.

  entre la interfaz de usuario, la lógica de negocio del backend y la simulación del robot.

  Diagnóstico del Problema

   1. Punto de Entrada (`entrypoint.sh`): El script carga correctamente los entornos de ROS (setup.bash) y
      luego ejecuta el archivo de lanzamiento principal ros2 launch orchestrator system_launch.py. Esto es
      correcto.
   2. Lanzamiento Principal (`system_launch.py`): Este archivo incluye tb3_simulation_launch.py de
      nav2_bringup, que es el lanzador estándar de Nav2 para el TurtleBot3. Pasa argumentos como slam:='False',
       map:=<ruta_al_mapa>, y autostart:='True'. Esto también es correcto.
   3. Dockerfile: Instala todas las dependencias necesarias, incluyendo nav2_bringup, slam_toolbox, etc. Esto
      parece correcto.
   4. El Problema Real: El archivo tb3_simulation_launch.py que viene con nav2_bringup en ROS 2 Humble tiene un
       comportamiento particular: inicia el stack de Nav2, pero no activa los servidores del ciclo de vida
      (lifecycle servers) por defecto. Los nodos de Nav2 se lanzan en un estado "unconfigured" (sin configurar)
       y esperan a que un "Lifecycle Manager" (gestor de ciclo de vida) los configure y active.

  El argumento autostart:='True' que se pasa en system_launch.py debería encargarse de esto, ya que se lo
  pasa al nav2_bringup_launch.py subyacente. Sin embargo, es muy común que esta activación falle
  silenciosamente si hay problemas de temporización (nodos que no están listos cuando el gestor intenta
  activarlos) o si falta alguna configuración específica.

  Cuando los nodos de Nav2 no se activan, el robot existe en la simulación, puedes teleoperarlo (como haces
  con el joystick), pero no responderá a los comandos de navegación (Initial Pose, Nav2 Goal) porque los
  servidores de planificación, control y comportamiento no están activos.

  Solución Propuesta

  La solución más robusta es modificar el system_launch.py para lanzar explícitamente el lifecycle_manager
  de Nav2 y darle la orden de activar los servidores necesarios. Esto elimina la dependencia de que
  autostart funcione perfectamente y nos da un control más directo.

  Voy a modificar turtlebot3-sim/orchestrator/launch/system_launch.py para añadir el nodo lifecycle_manager
  y la lógica para activar los servidores.

  Causa Raíz

  El problema es una condición de carrera durante el inicio. Varios nodos se inician en paralelo:

   * Gazebo (gzserver): Simula el mundo y el robot.
   * robot_state_publisher: Publica las transformadas estáticas del robot (ej. la relación entre base_link y
     base_scan).
   * Controlador de Tracción (turtlebot3_diff_drive): Publica la odometría (la transformada odom ->
     base_footprint).
   * Nav2 (amcl, costmaps, etc.): Necesitan todas las transformadas anteriores para funcionar.

  Lo que está sucediendo es que los nodos de Nav2 (map_server, controller_server, amcl, etc.) se inician y
  tratan de activarse antes de que el turtlebot3_diff_drive haya tenido tiempo de empezar a publicar la
  transformada de odometría (odom). Sin esta transformada, todo el árbol de TF está incompleto, y Nav2
  falla.

  Solución

  La solución es introducir un retraso controlado en el lanzamiento para asegurar que los componentes base
  del robot estén completamente operativos antes de que intentemos activar el stack de Nav2.

  Voy a modificar system_launch.py para añadir un TimerAction. Esto retrasará el inicio del
  lifecycle_manager por unos segundos, dando tiempo a que Gazebo y los controladores del robot se
  estabilicen. Un retraso de 5 segundos suele ser suficiente.

  Localización vs. Simulación

   1. Mundo de la Simulación (Gazebo): Gazebo es como el "mundo real". El modelo del robot en Gazebo tiene una
      posición física. Esta posición solo cambia si las ruedas del robot se mueven, es decir, si recibe un
      comando de velocidad (como cuando lo mueves con el joystick). El robot en Gazebo nunca se
      teletransportará.
   2. Mundo de la Localización (Nav2/AMCL): AMCL es el cerebro de la localización. Mantiene una hipótesis de
      dónde cree que está el robot en el mapa. Esta hipótesis se representa como la transformada de map a odom.
   3. El "Initial Pose": Cuando envías un Initial Pose, no le estás diciendo a Gazebo "mueve el robot aquí". Le
       estás diciendo a AMCL: "Olvida dónde creías que estabas. A partir de ahora, tu nueva posición de
      referencia en el mapa es esta".

  El resultado es que el árbol de transformadas (TF) se actualiza, pero el modelo en Gazebo no se mueve. Tu
  interfaz de usuario, que visualiza la posición del robot basándose en el TF, debería mostrar al robot
  "saltando" a la nueva ubicación en el mapa que se muestra en la UI.
